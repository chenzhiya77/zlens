# T26 — 运行质量页画布重排 + 来源维度

**Blocked by:** None —— 后端能力已就位(T09/T10 多源适配、T18 来源枚举、`/api/performance` 与 `/api/health` 的 `?source=` 参数)
**Status:** done (2026-08-30)

## User story

作为多 agent 用户,我想在运行质量页按 agent 分别看质量:默认「全部」是系统现状
(合并口径),点页头来源 chips 切到单个 agent 看它的明细;再有一张恒驻的「分源对比」
表,让我不切换就能看出 zcode / minimax / opencode 谁跑得稳。

## 视觉事实源

Ardot 文件「运行质量2」(`cocraft://localhost/file/720202836547247`)顶层画框
**2:2「zlens 运行质量-优化稿」**(1440×1190,浅色)。实施时用 Ardot MCP 逐节点比对,
节点 3:1–3:9 为来源 chips、3:10 为分源对比卡;实现以画布为准,画布演示数字
(3,250 / 7.8% 等)是编的,不代表阈值与真实库。

## What to build

后端零改动(`?source=` 已存在)。本票全部是前端 + API 封装:

1. **页面结构按画布重排**:`App.tsx` 给 `/runtime` 加 `ownTitle: true`,页内自绘页头
   (标题 + 副标题「累计口径 · 数据库共 N 次模型请求」+ 刷新控件)。其下依次:
   健康结论栏(总体状态点 + 错误率/重试率/取消率)→ 请求耗时 / 首字延迟两卡
   (P50/P90/P99 条,**单一强调色**,条长按本卡 P99 归一,样本数在标题行右侧,
   卡底刻度说明)→ 三张统计卡(模型请求总数 / 含重试的请求 / 出错请求,各带
   说明副行:取消·超限、重试总次数·平均、错误率·首位错误)→ 分源对比卡 →
   错误类型分布卡(标题「错误类型分布 · 来源:X」)→ 底部口径注释。
2. **比率是纯计数除法,前端算安全**:错误率 = errored/request_count 等,与 T24
   合计口径无关,不触碰"未计价则 null"规则。**零值变暗**(0.0% 用次级灰),
   非零出错率用红色——延续总览页既定规则。
3. **来源 chips**:全部 / zcode / minimax / opencode,数据来自 `meta.sources`;
   不可用置灰 + title 显示原因;**只有部分源可用时只渲染可用的**。切换 =
   performance / health / meta 请求带 `source` 参数,全部卡片由后端重算;
   **禁止前端取合并数据后本地拆分**。`source` 进 URL query(复用 Overview 的
   持久化模式),刷新/前进后退/分享可还原。
4. **API 封装**:`fetchPerformance` / `fetchHealth` 增加 `ViewQuery` 参数,
   走既有 `viewQueryString`。
5. **分源对比卡**(不受 chips 影响,恒显示全部可用源):对每个可用源并行请求
   `/api/health?source=x` 与 `/api/performance?source=x`(react-query,queryKey
   带 source),列 = 来源 / 请求总数·占比 / 重试率 / 出错率 / 取消率 / 耗时 P99 /
   首字 P99 / 状态(彩点+词)。占比与三个比率是前端除法;P99 直接用后端
   `latency_stats` 结果,前端不算分位数。卡底固定口径注:小样本来源分位数
   波动大,对比看趋势不看绝对值。**仅一个可用源时整卡隐藏**(无对比对象)。
6. **状态点阈值**(组件顶部常量,健康结论栏与对比卡行级共用):出错率 <5% 绿
   「总体健康/健康」;<15% amber「有波动/偏高」;≥15% 红「需要关注/异常」。
   画布 demo 的点色若与阈值冲突,以本阈值为准。
7. **自动刷新**:本页查询 `refetchInterval: 300_000`,刷新控件文案
   「自动刷新 · 5 分钟」必须与真实行为一致。
8. **API 类型定义**同步(`LatencyStats` / `HealthReport` 已有,核对无需新增字段)。

## Out of scope

- **时间范围 seg(近 1 小时/24 小时/7 天)**:画布画了,但 `/api/performance`、
  `/api/health` 无窗口参数,加窗口要动三个适配器的采样与计数查询,另开票。
  本次**不渲染该控件**——渲染一个点了没反应的控件等于撒谎;副标题「累计口径」
  与此一致。
- 后端任何改动(含分源聚合端点:每源两请求 × 3 源共 6 个并行请求,量级无压力,
  为此扩 response model 不值)。
- 画布中未画的功能(错误行点开明细等)。

## Architectural decisions

- **分源 = 后端参数,不是前端拆分**。`?source=` 是 MultiSource 已有的正式口径,
  前端拿合并数据本地分组必然复刻一份聚合逻辑,迟早和适配器口径漂移。
- **分源对比卡是展示层编排**:N 个源的独立请求 + 纯除法比率,不引入后端聚合端点;
  P99 必须来自后端 `latency_stats`,前端只做除法和展示。
- **URL 是唯一视图状态容器**(同 T24):本页状态只有 `source` 一项。
- **画布是视觉事实源,票是口径事实源**:演示数字、demo 点色与真实数据冲突时,
  以本票的阈值规则与真实 API 返回为准。
