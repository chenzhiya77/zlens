# zlens 总览页改版规格：设计稿 → 后端能力缺口

- 设计稿：Ardot `719793184410961`「AI用量总览-优化版」（画布根节点 `2:1`，1440 宽，单页）
- 规格日期：2026-08-28 · 更新：2026-08-29
- 状态：**已定稿**（Q1–Q6 见 §7，追加三项见 §8），无遗留问题，可拆实施票 · 关联票：待拆（T14+）
- 前置：v1-spec.md / v2-multi-source-spec.md / v3-credit-sources-spec.md
- 本规格只回答一件事：**设计稿上画出来的东西，后端现在还没有哪些**。前端改版方案不在本文范围。

## Problem Statement

设计稿是一张信息密度更高的总览页（Hero 主指标卡 + 5 张 KPI 卡 + 模型明细表），
比现有 `frontend/src/pages/Overview.tsx` 多画了 5 类交互：周期选择、环比、来源 chips、
按成本排序、合计行，外加一个导出按钮。这些控件背后有 8 项后端能力目前不存在
（最关键的：全站没有任何日期窗口参数）。照着设计稿直接写前端，这些控件只会是死控件。

结论先行：**改版必须两阶段走**。阶段 A 只做视觉层替换（Hero + KPI 卡 + 表格，逻辑零改动）；
阶段 B 后端补齐本文 G1–G9 后再接交互控件。

## 2. 缺口清单

### G1 日期窗口参数（P0 · 阻断）

- **现状**：所有 GET 端点只有 `source` 一个查询参数（`grep -n "Query("` 全库仅 6 处，全是 source）。
  适配器协议 `SourceAdapter` 也没有窗口概念，zcode 的 SQL 直接 `FROM model_usage` 扫全表。
- **决定**：`overview` / `trends/daily` / `models` 三个端点新增 `start` / `end`
  （`date | None`，ISO `YYYY-MM-DD`，闭区间，按本地日切）。缺省 = 全量，行为与今天完全一致。
  `meta` 同步接受窗口，让首末请求时间反映窗口而非全库。
- **周期选择器选项（Q1 已定）**：`近 7 天` / `近 30 天` / `近 90 天` / `全部` / `自定义区间`。
  「全部」= 不带 `start` / `end`（走全量分支，与今天行为一致）；其余四项都由前端翻译成具体日期。
  **后端只认日期，不认「近 N 天」这种相对表达式** —— 相对窗口的锚点是"今天"还是"最后一条请求
  时间"是产品决定，不该由 API 猜。
- **下推**：窗口必须下推到适配器（zcode `started_at`、minimax 事件毫秒时间戳、opencode
  `time.created` 都有日切依据），**不允许在 API 层拿全量行再过滤** —— `daily_by_model()` 是
  按日聚合的，外层过滤会破坏"某天未计价则该天成本为 null"的判定。
- **验收**：`?start=2026-07-30&end=2026-08-28` 返回的 `total_tokens` 等于该区间各日之和；
  窗口外无数据时各计数为 0、`by_model` 为空数组（不是 500）。

### G2 环比 / 上期对比（P0 · 阻断）

- **现状**：设计稿有 2 处环比（Hero `2:17`、KPI1 `2:31`），后端无任何上期概念。
- **决定**：`Overview` 新增 `delta: PeriodDelta | None`。上期窗口 = 当期窗口**向前平移等长天数**
  （如近 30 天 → 前 30 天）。`PeriodDelta` 只带两个字段：`request_count`、`estimated_cost`，
  每个形如 `{ previous: number | null, change_rate: number | null }`。
- **为什么用等长前移（Q5 已定）**：另一种做法「自然月对齐」（本期 8/1–8/28 对上期 7/1–7/31）
  两期天数不同（28 vs 31），直接比总量会因为天数差而显示假涨跌。等长前移保证两期天数相同，
  总量可直接相除，不需要做日均归一化。
- **硬规矩**：
  - **上期窗口必须完整落在数据范围内，否则 `delta = null`**（Q5 延伸决定）。部分有数据的上期
    算出来必然是"暴涨"，但缺的那些天不是"没用量"，是"那会儿还没装这个工具"——显示它就是撒谎。
    这条与"未计价即 null"是同一条原则：**宁可不显示，也不显示一个假数字**。
    判定依据：`meta.first_request_at <= 上期窗口起点`（按本地日切比较）。
  - 上期窗口内无数据 → `delta = null`，前端不渲染环比，**不允许显示 "—%" 或 0%**。
  - 当期或上期任一侧 `estimated_cost` 为 null → 该字段 `change_rate = null`（未计价就是不知道，
    不是"没涨"）。
  - `change_rate` 为 null 时 `previous` 仍可给出（用户至少能看到上期绝对值）。
  - 「全部」窗口下不做环比：上期无从定义（数据之前没有数据）。
- **禁止**：前端拿 `/api/trends/daily` 自行切片算环比。分母口径（未计价 null、四档归一）
  只有后端知道，前端重算必然算出另一个数。

### G3 趋势 mini 图（P1 · 依赖 G1）

- **现状**：`/api/trends/daily` 已返回 `days[].estimated_cost`，数据够用。
- **决定（定长窗口：7/30/90 天 + 自定义）**：不新增端点。前端用 `?start=&end=` 取窗口内日序列，
  画折线图，ECharts 设 `connectNulls: false` —— 未计价的日子成本是 null，折线必须**断口**，
  补 0 等于画一条假的下降。
- **决定（「全部」窗口：改按月聚合的柱状图）**。全量可能跨好几个月甚至一年，
  "近 30 天趋势线"的语义在这里失效，画成日折线会得到一根密到看不清的锯齿。
  **由后端出月度序列，不是前端拿日序列自己加一遍**：月粒度的 null 规则是
  「该月内任一天未计价 → 该月为 null」，这条规则若由前端重算，就又是在前端抄了一份口径
  （与 §4「所有聚合仍在后端」冲突）。
  - 落地：`/api/trends/daily` 增加 `granularity` 参数（`day` 默认 | `month`），
    在 `core/cost.py` 里与 `fold_daily` 并列加一个 `fold_monthly`，**复用同一条未计价判定**，
    只是把 key 从 `day` 换成 `YYYY-MM`。不新增端点。
  - 前端：定长窗口 → 折线（按日）；「全部」→ 柱状图（按月）。
    x 轴标签用 `2026-03` 这种短月份，月份多时允许横向滚动。

### G4 来源枚举（P1）

- **现状**：chips 需要可用来源列表，但只有 `meta.source_id`（`"zcode+minimax+opencode"` 拼接串），
  前端靠 split 解析很脆，而且拿不到"某个源不可用及其原因"。
- **决定**：`MetaInfo` 新增 `sources: list[SourceRef]`，`SourceRef = { id, available, error: str | None }`。
  `source_id` 保留不动（v2 契约，别破坏）。首屏本来就拉 meta，多一个数组不增加请求。
- **验收**：minimax 目录缺失时，chips 仍列出三项，minimax 置灰并带 `error`。

### G5 来源过滤（✅ 已具备）

`/api/overview`、`/trends/daily`、`/models`、`/meta`、`/projects`、`/performance`、`/health`
**都已支持 `?source=`**。这一项不是后端缺口，是前端没接线（`Overview.tsx` 拉的
`fetchOverview()` 不带参数）。切换 chip 时所有卡片与表格必须由**后端**重算，
**禁止前端拿 `by_model` 本地 filter 后自己求和** —— 那会绕过"任一渠道未计价则总额为 null"。

### G6 排序（P1）

- **现状**：`multi.overview()` 与 `models_ranking()` 都按 `total_tokens` 降序。设计稿副标题要求
  「按成本降序」。
- **决定**：`overview` / `models` 新增 `sort` 参数（`total_tokens` | `estimated_cost` | `request_count`）
  与 `order`（`desc` | `asc`），**默认 `sort=total_tokens&order=desc`**，避免改动既有视图行为。
  未计价行（`estimated_cost = null`）**恒排最后**，与升降序无关 —— 它们是"不知道"，
  不该混进排序中间。
- **表头点击排序（Q2 已定：要）**：表头可点的列为「请求数 / 输入 / 输出 / 缓存写 / 缓存读 /
  总计 / 成本(估算)」，点击切换升降序，二次点击反向。默认 `成本(估算)` 降序（对齐设计稿
  副标题「按成本降序」），并在该列显示排序指示。**排序状态与 `sort` / `order` 参数一一对应，
  由后端排序，不是前端 `Array.sort`** —— 否则未计价行"恒排最后"的规则会在前端被漏掉一次。
- **排序状态持久化（已定：需要）**：`sort` / `order` / `source` / 窗口**全部进 URL query**
  （react-router 的 `useSearchParams`）。刷新、前进后退、把链接发给同事都能还原同一张表。
  这是总览页唯一的视图状态，没有别的需要持久化。
- **设计稿要补的东西**：表头目前没有排序视觉提示（无箭头 / 无 hover 态），需在画布上补一个
  排序指示器样式（含升序/降序两种箭头）。

### G7 合计行（P1）

- **现状**：无合计对象。设计稿 `4:66` 的文案「本页合计 · 前 5 个模型」还和副标题「共 14 个模型」
  自相矛盾（画布实际只画了 5 行示意）。
- **决定**：
  1. **不做分页**。模型数本来就是十几个量级，分页是纯负担。合计行文案改为「全部合计 · 共 N 个模型」。
  2. 由后端在 `Overview` 里返回 `totals: OverviewTotals`（`request_count` 与六个 token 档 + `estimated_cost`），
     **不是让前端把 `by_model` 加一遍**。
  3. 合计沿用同一条诚实规则：任一模型未计价 → `totals.estimated_cost = null`，
     而 token 各档照常给出（它们不依赖价格表）。
- **验收**：把某个渠道的价格从 `pricing.json` 删掉 → 合计成本变 null，token 合计不变。

### G8 缓存命中率（P1）

- **现状**：KPI3 `2:37` 显示「缓存命中率 94.7% (按 token 计)」，后端无此字段。
  ⚠️ **这是新增指标，不是修复既有 bug** —— 现有代码里没有任何"算错的命中率"在跑，
  设计稿上那个 94.7% 是画上去的。实施时不要去找"哪里算错了"，是从零加一个字段。
- **口径**：适配器已归一为四档互斥（zcode 交出 `input - cache_read - cache_creation`，
  见 `zcode.py:62` 的 `_AGGREGATE_SQL`），所以 prompt 侧 token = `input + cache_read + cache_creation`。

  ```
  cache_hit_rate = cache_read / (input + cache_read + cache_creation)   分母为 0 → null
  ```

  验算：设计稿 KPI 卡 累计 5.49 亿 / 输出 148.9 万 / 缓存读 5.20 亿 / 缓存写 0
  → 分母 = (5.49 亿 − 148.9 万) = 5.475 亿 → 5.20 / 5.475 ≈ 94.97%，与设计稿 94.7% 吻合。
- **分母之争（Q6 已定：含缓存写，即方案 A）**：
  - 方案 A（采用）：`cache_read / (input + cache_read + cache_creation)`
    语义：**你的 prompt 里有多大比例是白嫖缓存来的**，分母 = 全部 prompt token。
  - 方案 B（否决）：`cache_read / (input + cache_read)`
    语义：在"本来有可能命中"的 token 里有多大的比例命中了 —— 把 `cache_creation` 当作
    "第一次见这段内容，本来就没机会命中"而排除。
  - 取舍：B 的数字更好看（上例 88.9% vs 80.0%），但它把「写缓存」这份开销从分母里抹掉了。
    **成本工具不该美化成本指标**。且 A 的分母恰好等于"prompt token 总量"，与四档相加 =
    `total_tokens` 的契约天然对齐，不会引入第二个口径。
  - **决定性理由（价格表实证）**：`pricing.example.json` 里 `claude-sonnet-4-5` 的单价是
    `input: 21.6` / `cache_read: 2.16` / `cache_write: 27.0` —— **缓存写比普通输入还贵**。
    B 把它踢出分母，等于把 prompt 里最贵的那一档藏起来，而那恰好是最该被看见的部分。
  - **B 会输出语义上不可能的数字**：当 `input = 0` 且 `cache_creation > 0` 时，B 的分母
    = `cache_read`，命中率恒为 **100%** —— 而此时用户正按最贵的缓存写单价付费。
    「命中率 100% 但仍在付费」自相矛盾；A 不会，它如实把那部分算进分母。
  - 影响面：只有 `cache_creation > 0` 的渠道会分叉。zcode 恒为 0（两种算法结果相同，也是
    上面验算能对上 94.7% 的原因）；但 `claude-sonnet-4-5` 这类渠道有缓存写，会分叉。
- **决定**：`Overview.cache_hit_rate: float | None` 与 `ModelUsageSummary.cache_hit_rate: float | None`
  （行级可选，表格未来要展示时用）。**定义在后端，前端只负责格式化成百分比。**
  展示带一句口径说明「按 token 计」，避免被误读成"请求命中率"。

### G9 买断支出：null/0 与结清日期（P0 / P2）

- **(a) null 与 0 不可区分（P0，这是正确性 bug，不是改版需求）**
  `Overview.buyout_total: float = 0.0`（`sources/models.py:56`）——价格表里一条买断行都没有时
  返回 `0.0`，与"买了但花 0 元"长得一样。前端现在用 `o.buyout_total === 0 ? "未填" : "已付清"`
  猜，这是把「没填」显示成「未填」的巧合，一旦有人真填了 0 就会显示成「已付清」。
  与 AGENTS.md「留空(null)与填 0 必须可区分——把没填显示成 ¥0.00 就是撒谎」直接冲突。
  **决定**：`buyout_total` 改为 `float | None`；`PriceTable.buyout_total()` 在**没有任何非 null
  `buyout_amount` 行**时返回 `None`。展示：null → 「未填」，0 → 「¥0.00 · 免费套餐」。
- **(b) 结清日期（P2）**：`ModelPrice` 只有 `buyout_amount`，没有付款日期，
  设计稿「已结清 · 2026-08-20」无数据来源。**决定：先从设计稿删掉这句**；确需再给价格表行加
  可选 `buyout_paid_on: date | None`（缺失就不显示日期，不猜）。

### G10 导出（P2）

- **现状确认**：后端 `grep -n "export" src/zlens` 零匹配，前端也只有 TypeScript 的 `export`
  关键字。**这个功能目前完全不存在**，设计稿 `2:8` 的按钮纯装饰。
- **决定（Q3 已收敛）**：**只做 md**。`GET /api/export`，固定输出 Markdown 表格，
  复用 `start` / `end` / `source` / `sort` / `order` 参数，内容为按模型明细（`by_model` 全字段）。
  不做 csv，也不保留 `format` 参数 —— 本机单机工具的导出主要去处是贴进笔记/周报或喂给 LLM，
  md 更对路；csv 的强项（进 Excel 做透视）这里用不上，砍掉省一半代码。将来真要 csv 再加，
  届时属于新增能力而不是删减。
- **硬要求**：
  - **null 的表示**：md 里写「未计价」。**不能是 `0` 或 `0.00`** —— 导出的数字会被拿去做账，
    写 0 就是把"不知道"固化成"免费"。
  - **只导原始整数**：token 列导 `549382910` 而不是 `5.49 亿`，成本列导 `21.22` 而不是
    `¥ 21.22`。导出是给人二次加工的，格式化过的数字不可再算。
  - **别名不进导出**：别名是 localStorage 里的客户端状态（`frontend/src/lib/alias.ts`），
    后端不知道它存在。只导出 `model_id`，并在文件头注明别名未包含。
  - md 导出的表头需带一行口径说明（四档互斥、成本为估算值、未计价的含义），
    否则这张表脱离应用后会被误读。

### G11 自动刷新（P1）

页脚承诺「每小时刷新一次」，但 `Overview.tsx` 的 `useQuery` 没有 `refetchInterval`。
**决定**：总览与趋势查询加 `refetchInterval: 3_600_000`；文案与真实行为绑定，
不写死承诺（若将来改成手动刷新，文案必须同步改）。

### G12 未计价渠道提醒条必须补回（P0）

设计稿没有这块，但现有页面有（`Overview.tsx:84`，数据来自 `meta.unpriced_models`）。
在"成本可能是 null"的产品里，这条是**可信度提示**，删掉它用户会以为看到的就是全部账单。
**决定**：保留，位置挪到 Hero 卡下方作为 inline notice；切换来源/窗口时跟着走
（`meta` 端点已支持 `source`，窗口参数见 G1）。

## 3. 设计稿自身缺陷（实现时必须纠正，别照抄像素）

- **D1 表格列值错位（严重）**。表头显示顺序是 输入 / 输出 / 缓存写 / 缓存读 / 总计 / 成本，
  但数据行 1（`2:83`）的实际值是 252.4 万 / **1.72 亿** / 0 / **32.6 万** / 1.75 亿 / ¥21.22。
  按 zcode 真实口径（缓存读 ≫ 输出，缓存写 = 0），正确应为
  **输入 252.4 万 · 输出 32.6 万 · 缓存写 0 · 缓存读 1.72 亿**。
  画布节点名也印证了错位：`R1-缓存读` 装的正是 1.72 亿，`R1-输出` 装的是 0，
  而 `表头-缓存读` 的文字却是「输出」。
  **该结论已被真实 UI 截图验证**：同一条 `glm-5.3-flash` 记录在实际数据中为
  输入 252.4 万 / 输出 32.6 万 / 缓存写 0 / 缓存读 1.72 亿（2026-08-29 截图），
  与设计稿的 1.72 亿 / 32.6 万 正好互换。
  **以四档互斥的数据口径为准，不要照抄画布像素位置。**
- **D2 残留的「命中率」列**。节点名 `表头-命中率` / `合计-命中率` 还在，显示文字已改成「缓存读」，
  合计行该格放的是 428.5 万（token 数，不是比率）。最终列集确认为
  **来源·模型·别名·请求数·输入·输出·缓存写·缓存读·总计·成本(估算)**，共 10 列。
- **D3 合计行文案「本页合计 · 前 5 个模型」与副标题「共 14 个模型」矛盾**（见 G7，改为不分页 + 全量合计）。
- **D4 Hero 估算口径文案漏项**。`2:18` 写「输入 token + 输出 token + 缓存读 token」，
  漏了**缓存写**。成本公式是四档逐档乘价（`cost.estimate_cost`），文案改为
  「输入 + 输出 + 缓存写 + 缓存读 四档分别乘价求和」。
- **D9 Hero 标题用词（Q4 已定）**。设计稿 `2:15` 写「本期预估支出 (CNY)」，**统一改为「按量消耗 (CNY)」**，
  沿用现有页面的术语。理由：与 KPI5「实购支出」形成"两笔钱"的对照，且「预估」二字会弱化
  数字的可信度 —— 这个数本来就是估算，再挂个"预估"反而让人不信任。
  同理 KPI5 的「实购支出」保留，两处措辞形成明确对照，体现"两笔钱永不相加"。
- **D5 成本列用红色**。数据行 `2:103` 的 ¥21.22 用了 `#EF4444`。本项目里红色是
  「上涨 / 告警」语义（Hero 环比上涨也是这个红），把金额本身染红会与环比语义撞车。
  **建议**：金额用中性深色，只有**变化量**用红/绿。
- **D6 缺未计价提醒条**（见 G12）。
- **D7 版本号硬编码**「v2.0」→ 用 `zlens.__version__`。
- **D8 缓存写列当前恒为 0 —— 三源实测确认，但这一列必须保留**。

  2026-08-29 对本机三个真实数据源的只读实测（探针脚本见 `scratch/*_cachewrite_probe.py`）：

  | 源 | 规模 | 缓存写 | 缓存读 |
  |---|---|---|---|
  | zcode | 2737 行 / 10 模型 | **恒 0**（`MAX = 0`，0 行非零） | 521,786,432（2580 行非零） |
  | opencode | 4 行 | 0 | 1,024（1 行非零） |
  | minimax | 5 会话 | 0 | 109,778 |

  **不是提取不出来，是上游没给非零值**。追到 zcode 的原始 payload（`raw_usage_json`，
  驼峰命名）后可知：
  - 多数模型（glm-5.3-flash 等）的 payload 里**只有** `cacheReadTokens`，连字段都没有；
  - 只有 Kimi-K3 的 89 行带 `cacheWriteTokens` 字段，而这 89 行的值
    **sum = max = min = 0**，从来没非零过。

  两层含义：
  1. **Q6 的 A / B 之争在用户当前数据上完全无差别**（缓存写恒 0，两种算法给同一个数）。
     选 A 不付任何代价，纯粹是给将来买保险；
  2. **不是纯理论** —— 三个源的协议里都有缓存写字段，只是当前 provider 没触发
     （大概率是没显式设置 cache breakpoint）。一旦某个模型开始写缓存，差别立刻显现，
     而 B 会输出「命中率 100% 但仍在按缓存写单价付费」这种自相矛盾的显示。

  ⚠️ **一个无法从现有数据证伪的风险**：89 行里有 `cacheWriteTokens` 字段，
  而 `cache_creation_input_tokens` 列同样是 0。这只能证明"值恰好是 0"，
  **不能证明 ZCode 会把非零值透传到那一列**。若将来上游开始报非零而 ZCode 丢弃，
  zlens 会静默漏掉这部分成本。届时可从 `raw_usage_json` 补捞，但今天没有证据，不做。

  另外：v3 积分类来源引入后必须能区分「上游上报 0」与「上游不支持该档」
  （v3 spec §Problem Statement 第 2 点的同一个问题）。改版时别把 0 渲染成灰色的
  "无意义"样式，那会提前堵死 v3 的表达空间。

## 4. Implementation Decisions

- **两阶段交付**：阶段 A 纯视觉替换（表格 + Hero + KPI 卡，全部走现有字段，零后端改动）；
  阶段 B 后端补齐 G1–G9 后接交互控件。禁止一次上齐。
- **窗口优先于其它一切**：G1 是 G2 / G3 / G7 的前置，先做。
- **所有聚合仍在后端**：来源过滤、窗口、排序、合计、环比、命中率全部由 API 出结果。
  前端只做格式化与纯客户端的搜索/别名。这条是对 AGENTS.md
  「现总价一律从 /api/overview 取，禁止在前端重算一份公式」的延伸，不只是针对价格表页。
- **适配器只读不变**：窗口下推不改变 `mode=ro` 约束，也不新增任何写入路径。
- **null 的三种表情要分清**：未计价（null）→ 「未计价」徽章 / 空单元格；未填（null）→「未填」；
  真 0 → 正常显示 `¥0.00` 并附说明。任何一处把前两者画成 0 都是 bug。

## 5. Testing Decisions

按 AGENTS.md：测试落 `tests/`，扁平命名 `test_<feature>.py`，读真实库的打 `@pytest.mark.live`。

- `test_overview_window.py`：窗口边界（首日/末日/单日/窗口外）、窗口内无数据返回空 `by_model`、
  窗口和等于各日之和。
- `test_overview_delta.py`：上期有数据、上期为空（`delta=null`）、当期未计价
  （`change_rate=null` 但 `previous` 仍在）、上期为 0 时变化率的除零保护。
- `test_overview_totals.py`：全计价 → 合计为数；任一模型未计价 → 合计成本 null 而 token 合计不变。
- `test_cache_hit_rate.py`：命中率公式、分母为 0 → null、四档归一后的取值（fixture 必须按真实
  形状写：zcode 的嵌套形状要照写嵌套）。
- `test_buyout_null_vs_zero.py`：无买断行 → `buyout_total=None`；`buyout_amount: 0` → `0.0`；
  两者并存 → `0.0`。这是回归测试，防的是"把没填显示成 ¥0.00"。
- `test_sources_enum.py`：`meta.sources` 列出全部已注册源，不可用的带 error 且 `available=false`。
- `test_overview_sort.py`：`sort=estimated_cost` 时未计价行恒排最后；默认排序行为不回退。
- `test_zcode_clamp_per_row.py`（**补测试，不是改逻辑**）：zcode 适配器的逐行兜底。
  `zcode.py:62` 的 `MAX(..., 0)` 包在 `SUM` **里面**，`zcode.py:58` 的注释也写明了意图
  「a single malformed record must not be able to offset a good one into a negative」，
  但**现状没有任何测试锁住它** —— 现有 fixture 全是合法行（`tests/test_overview.py` 三行
  都满足 `cache_read + cache_creation <= input_tokens`）。
  用例：混一行 `cache_read + cache_creation > input_tokens` 的脏数据，断言该行贡献的
  `input_tokens` 为 0，且其它正常行的 input **不受影响**；同时断言把 `MAX` 挪到 `SUM` 外面
  会得到不同结果（证明这条测试真的在守这个行为）。
- 既有测试套件必须零改动通过（缺省参数 = 全量，行为与今天一致）。
- live 冒烟：真实库上 `?start=&end=` 与全量的 token 总数差异符合预期日期跨度。

### Q5 的延伸决定（本次新增，需复核）

原规格只写了"上期无数据 → `delta = null`"，但漏了**上期部分有数据**这种情况：
用户总共只有 40 天数据却选「近 30 天」，上期窗口里 20 天是空的，算出来必然"暴涨"。
缺的那些天不是没用量，是那会儿还没装工具。已按"宁可不显示也不显示假数字"的原则
收紧为：**上期窗口必须完整落在 `[first_request_at, 本期起点)` 内，否则 `delta = null`**。

### 追加说明：为什么按月聚合必须走后端

表面看"把日数据按月加一遍"是很轻的操作，但它要复用同一条未计价判定
（月内任一天未计价 → 该月为 null）。这条规则已经在 `fold_daily` 里存在，
让前端再实现一遍等于在界面层抄了一份成本口径 —— 正是 §4 明令禁止的。
所以改成 `/api/trends/daily?granularity=month`，与 `fold_daily` 共用一个未计价判定。
