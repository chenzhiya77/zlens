# zlens v2.4 规格：买断制模型的价格与成本口径

> 状态：**ready-for-agent** · 定稿：2026-08-27 · 前置：v1/v2 已交付（见
> `v1-spec.md`、`v2-multi-source-spec.md`）
> 实施票：T14（建议单票，见文末拆分建议）

## Problem Statement

zlens 的价格表只有「按量后付」一种口径：input/output/cache_read/cache_write 四档，
成本 = 单价 × 用量。但真实世界里有大量**买断模型**：固定金额买定量额度，钱在
购买时一次性付清，后续请求不再逐笔按单价扣费。现有结构无法表达这种模型——硬塞四档
要么算出错误的「每百万单价」，要么假装每笔请求都在扣钱。

用户的真实心智是：**买断模型「花掉的成本」就是买入时付的那笔钱**，一次性、恒定，
而不是消耗出来的。zlens 需要一种方式让用户为买断模型填「买入金额」，并让成本口径
诚实地回答两个不同的问题：**当前按量消耗了多少钱** 与 **买断一共花了多少钱**。

## Solution

价格表为每个模型新增 `billing` 维度，两种模式：

- **payg（默认，现有行为不变）**：input/output/cache_read/cache_write 四档，
  成本 = 单价 × 用量。
- **prepaid（买断）**：字段为 `买入金额(USD)`（必填）+ `买入量(tokens)`（可选）。
  成本列显示**买入金额**，标注「买断支出」；消耗量仍由真实库统计（这些请求确实
  发生过），与买入金额独立展示。**买断不换算成每百万单价，不算逐笔成本**。

总览成本区改为**两个总数并排**，分别回答用户区分过的两个问题：

1. **消耗成本（按量）** = Σ 仅按量模型的（单价 × 用量）。买断模型**不**计入。
2. **买断总支出** = Σ 买断模型的买入金额。

每个买断模型行：成本列 = 买入金额 + 「买断」标签；若填了买入量，额外显示
「已用 X / 买入 Y（剩余 Z）」。

## Implementation Decisions

- **billing 字段默认 `payg`，向后兼容**：既有 pricing.json 条目不变仍是按量，
  无需迁移；`PriceTable`/`ModelPrice` 增加可空 `billing`、`prepaid_amount_usd`、
  `prepaid_tokens` 字段。
- **prepaid 校验**：`prepaid_amount_usd` 必填且非负；`prepaid_tokens` 可选且非负。
  PUT pricing 时校验（沿用现有 422 语义）。
- **消耗量口径不变**：所有模型（含 prepaid）的 token 消耗仍来自真实库统计——这是
  工具本职（用户通过查看订单得知购买总数，zlens 通过库得知实际消耗）。
- **未计价逻辑不变**：价格表有该模型条目（无论 payg 还是 prepaid）即视为已计价，
  不计入 `unpriced_models`；买断模型不会因为「没有四档单价」而被误标未计价。
- **两个总数为什么分开**：买断的钱一旦付清就不再逐笔变化，把它混进「按量消耗」
  会让总览的「消耗成本」既像按量又像固定支出，语义混淆。分开后各自诚实，
  与用户口中「两种总价」的心智一致。
- **不做包均价摊销**：prepaid 的「每百万等效单价」（= 买入金额/买入量）不参与任何
  成本计算，也不建议前端主动展示——用户要的是「我花了多少钱」，不是「摊到每百万
  多少钱」。若未来真要比较买断是否划算，作为单独视图再做，不进成本列。/b>

## API Contract 变更

- `PUT /api/pricing` 与 `GET /api/pricing` 的 `ModelPrice` 增加：
  `billing?: "payg" | "prepaid"`、`prepaid_amount_usd?: number | null`、
  `prepaid_tokens?: number | null`。
- `GET /api/overview` 响应新增两个字段（总数）：
  `cost_consumed_usd`（按量消耗成本）与 `cost_prepaid_total_usd`（买断总支出）；
  现有 `estimated_cost_usd` 保留为**按量口径**（= cost_consumed_usd，兼容既有调用）。
- overview 的 `by_model` 行内，prepaid 模型：
  `estimated_cost_usd` = 其买入金额（标注在响应中可通过 `billing` 字段区分），
  `prepaid_remaining_tokens`（可空，有买入量时 = 买入量 − 已消耗）。

## Testing Decisions

- 沿用唯一 seam（HTTP API + fixture 库）。新增用例：
  - `PriceTable` 载入含 prepaid 条目的 pricing.json，字段落位正确；
  - PUT 校验：prepaid 缺金额 → 422；金额为负 → 422；纯 payg 条目不受影响；
  - overview：纯按量 → `cost_consumed_usd` 正确、`cost_prepaid_total_usd`=0；
    混合 → 两个总数分别正确，prepaid 行成本 = 买入金额且 billing=prepaid，
    未计价清单不含 prepaid 条目；
  - 填了买入量的 prepaid 行：`prepaid_remaining_tokens` = 买入量 − 已消耗；
  - 前端：价格表页买断行表单（金额必填、量可选）、总览双总数并排、买断行
    「买断」标签——`make check`（含前端构建）全绿。

## Out of Scope

- 包均价摊销、与按量的「等效单价」对比视图（用户明确不需要，避免假装精确）；
- 超量按量计费（prepaid 超额后转 payg）：v2.4 不做——用户方案是「买断模型
  用完就是用完」，超额处理留待未来票；
- 自动识别「这张截图是买断价还是按量价」：extract 输出继续标注 billing 由用户
  确认（v2.3 已有提示词约束）。

## Further Notes

- 用户方案原文：买断模型由用户在价格列表的「买入」列填金额；购买总数通过自己
  查看订单得知。本 spec 正是把它落成结构——买入列 = `prepaid_amount_usd`，
  订单购买总数 = 用户填的可选 `prepaid_tokens`（用于显示剩余量）。
- 诚实原则贯穿：买断成本显示买入金额并明示口径（「买断支出」），不算包均价、
  不假装摊销——延续 zlens「不硬编错价」的架构红线。
